# GoOnlinePOS AI Marketing Agent

An autonomous marketing system built **around** GoOnlinePOS, in its own
directory, on its own stack. It reads the real GoOnlinePOS source to build a
verified feature inventory, and (in later phases) will turn that inventory
into short-form marketing video ideas, scripts, and eventually
dry-run-then-real social posts.

**This directory never modifies GoOnlinePOS.** Everything here treats the
repo root (`app.html`, `modules/`, the marketing pages, etc.) as read-only
source material - see [Safety rules](#safety-rules) below.

**Status: Phases 1, 4, and 5 complete.** Product analysis, idea generation,
script generation, and free local video rendering all run end to end today.
Phases 6-9 (publishing, analytics, the full agentic loop) are still a
*design*, not yet working code - each stub module says so explicitly. See
[Roadmap](#roadmap--whats-not-built-yet).

## Why Python, not Node.js/npm

The GoOnlinePOS project itself has no build step, no bundler, and no
`package.json` - confirmed by inspecting the repo root before writing a
single line of this agent (see `../CLAUDE.md`'s own "Repo layout": *"Static
site... served straight from this repo... no build step, no bundler, no
package.json"*). Bolting an npm-based CLI onto a sibling tool for a project
that deliberately has none would be inconsistent with how this codebase is
actually built. This agent uses plain **Python 3** with the standard
library (`argparse`, `json`, `re`, `pathlib`) for everything Phase 1 needs -
zero extra installs to try it.

## What GoOnlinePOS actually is (Phase 1 findings)

Inspected before writing any agent code:

- **Stack:** static HTML/CSS/JS, one `<script>` block per page, no
  framework, no bundler, no npm. A handful of self-hosted vendor libraries
  (`vendor/xlsx.full.min.js`, `jszip.min.js`, `jsbarcode.min.js`,
  `qrcode.js`, `supabase.min.js`) loaded via plain `<script src>` tags.
  Some logic is split into `modules/*.js` classic scripts (not ES modules,
  deliberately - see `../CLAUDE.md`).
- **Data/backend:** almost entirely client-side/local-storage. The one
  exception is an optional Supabase (Postgres) backend for the Account &
  Subscription (Premium) system, plus a couple of small Google Apps Script
  endpoints for the contact form / PayPal purchase verification / new-signup
  notification email. No SQL database is part of the *POS app's* own data
  model - it's `localStorage` (or an injected-host storage API) end to end.
  No app.html data ever needs a database read to work.
  - This is exactly why this agent also uses plain JSON files, not SQL -
    consistent with the project it's marketing.
- **Pages:** `app.html` (the POS itself), `customer.html` (a live
  customer-facing mirror), `end-of-day.html` (closing report),
  `invoice-generator.html` / `receipt-generator.html` /
  `barcode-generator.html` / `vat-calculator.html` /
  `pricing-calculator.html` (five free standalone tools), plus a marketing
  site (`index.html`, `blog.html` + articles, `contact.html`, `privacy.html`,
  `terms.html`).
- **Documentation:** `../CLAUDE.md`, a single, extremely detailed project
  log (300KB+) describing every feature, why it was built, and where it
  lives in the source - the single richest source of truth for what's real
  in this product. Used heavily to identify probe anchors below.

## The verified feature inventory

`knowledge/features.json` is generated by `scripts/analyze_product.py`,
which is the actual Phase 1 mechanism, not a one-off hand-written file:

1. A small, hand-curated Python list (`FEATURE_PROBES` inside the script)
   names each real feature and 1-2 **source-code anchors** that must exist
   for the claim to be true - a function name, an element id, a marker
   comment, a library file.
2. The script opens the referenced GoOnlinePOS files **as plain text**
   (never executes, never writes to them) and checks each anchor with
   `re.search()`.
3. Only anchors that actually match get written into
   `knowledge/features.json` as `"verified": true`. A feature is skipped
   from being trustworthy the instant even one of its anchors goes missing.
4. Re-running the script re-checks everything against whatever the source
   looks like *right now* - this is the "refresh when the code changes"
   mechanism the project needed. If GoOnlinePOS is later edited and a
   referenced function is renamed or removed, the next
   `analyze-product`/`refresh-features` run will flip that feature to
   `"verified": false` and print a warning, instead of silently keeping a
   now-false marketing claim around.

This is intentionally a **regex anchor-matcher**, not a real AST/static
analyzer - simple enough to build and reason about in a proof of concept,
honest about its own limits (documented in the script's own docstring), and
good enough to catch real drift (a renamed function, a removed feature).

Run it yourself:

```bash
cd ai-marketing-agent
python3 cli.py analyze-product          # (re)writes knowledge/features.json
python3 cli.py analyze-product --check  # verify only, exit 1 on any drift - useful for a pre-commit/CI check
python3 cli.py refresh-features         # identical alias
```

Every feature currently in the inventory (18 features as of Phase 1,
covering inventory management, product photos, bulk CSV/Excel import, USB
barcode scanning, split payments, per-sale discounts/tax-exemption, multi-
cashier support, sales history + End of Day reporting, Excel export, the
customer-facing screen, backup/restore, multi-currency, six-language
support including Arabic RTL, configurable paper size, the offline
download, the free Invoice Generator and Barcode/QR Generator tools, and
the Premium subscription/free-trial system) is directly traceable to a real
function, element, or file in the GoOnlinePOS source - see each entry's own
`"evidence"` array for exactly what was checked.

## How ideas are generated (Phase 4 - implemented)

`agent/idea_generator.py`'s `generate_ideas()` reads only
`agent.product_knowledge.list_features(verified_only=True)` - features whose
evidence currently checks out - and produces one idea object per feature,
each with a hook/topic/audience/problem/solution/script/CTA/visual
scenes/caption/hashtags/title, written to `ideas/<feature_id>.json`. Every
field is either copied from `knowledge/features.json` verbatim or built from
it via a small fixed template - no LLM call, no new claims invented. The CTA
wording is driven by each feature's own `is_premium` value, so a
Premium-gated feature is never described as plainly "free" (see Safety rule
5). `agent/content_planner.py`'s `plan_content()`/`select_next_idea()` then
sequences the generated ideas into `data/content_plan.json` (free features
first, since Phase 7's real analytics don't exist yet to rank by - the
placeholder heuristic is documented in the module's own docstring) and logs
the choice via `agent/logger.py`.

```bash
python3 cli.py generate-ideas                  # writes ideas/*.json for every verified feature
python3 cli.py generate-script <idea-id>        # e.g. bulk-product-import - expands one idea into a timed script
```

`generate-script` writes both `scripts_output/<idea-id>.txt` (a
human-readable shooting script - hook/problem/solution/timed beats/visual
scenes/CTA/caption/hashtags, plus a per-claim evidence checklist) and
`scripts_output/<idea-id>.json` (the same content, structured, for
`create-video` to consume).

## How videos are generated (Phase 5 - implemented)

A free, local pipeline - `agent/video/generator.py`'s `LocalVideoGenerator`
composes each script "beat" into a branded 1080x1920 (vertical 9:16) PNG
frame with Pillow (already free, already in `requirements.txt`), using
GoOnlinePOS's own real `:root` CSS design tokens (`--ink`/`--accent`/`--gold`)
so the video actually looks like it belongs to the product. Where a real
GoOnlinePOS screenshot exists for a feature (`FEATURE_SCREENSHOTS` maps 12 of
the 18 verified features to their matching `guide-*.png` file already in the
repo root), the SOLUTION beat composites that real screenshot in instead of
plain text - actual product UI, not a mockup. The frame sequence is then
encoded to an MP4 by a locally installed, free/open-source `ffmpeg` binary
(not bundled - a one-time system install, e.g. `apt install ffmpeg`/`brew
install ffmpeg` - not a paid API), each frame held on screen for its beat's
own script duration via ffmpeg's concat demuxer.
`FutureAIVideoGenerator`/`FutureTemplateVideoGenerator` remain empty adapter
classes for optional paid tools, added later only if the site owner chooses
to pay for one - never required.

There is currently no text-to-speech engine available in this environment
(`espeak`/`espeak-ng`/`festival`/`pico2wave` were all checked, none found),
so the first-generation videos are silent/text-driven (on-screen captions
carry every beat's message) rather than narrated - a reasonable future
enhancement, not a blocker for this free proof of concept.

## How to preview videos (Phase 5 - implemented)

```bash
python3 cli.py create-video <idea-id>   # e.g. bulk-product-import - requires scripts_output/<idea-id>.json to already exist
```

Writes `videos/<idea-id>.mp4` and prints the local path - open it in any
video player to review. Nothing is published anywhere; this is purely a
local file on disk.

## How publishing will eventually work (Phase 6 - not built yet)

**Dry-run only, by design, for the entire life of this proof of concept
until the site owner explicitly says otherwise.** `python3 cli.py
preview-publish <video-id>` will print exactly what *would* be posted -
title, description, hashtags, the video file path - to each configured
platform, without making any network call, matching:

```
DRY RUN:
Would publish to YouTube:
Title: ...
Description: ...
Video: ...
Hashtags: ...

DRY RUN:
Would publish to Facebook:
Caption: ...
Video: ...
```

### How YouTube OAuth will be added

Once `YouTubePublisher` (`agent/publishing/youtube.py`) is actually built,
real publishing will require `YOUTUBE_CLIENT_ID`/`YOUTUBE_CLIENT_SECRET`/
`YOUTUBE_REFRESH_TOKEN` in `.env` (see `.env.example`), obtained from a
Google Cloud project with the YouTube Data API v3 enabled - standard OAuth
installed-app flow, run once locally to mint the refresh token. Real
publishing will additionally require an explicit approval flag/prompt at
call time (Safety rule 9) - dry-run will remain the default even with
credentials present.

### How Facebook/Meta authentication will be added

Once `FacebookPublisher` (`agent/publishing/facebook.py`) is actually
built, real publishing will require `FACEBOOK_PAGE_ID`/
`FACEBOOK_PAGE_ACCESS_TOKEN` in `.env`, obtained from a Meta developer app
with the relevant Page permissions. Same explicit-approval-before-real-
publish rule as YouTube.

## Which parts are currently free

All of it - product analysis (Phase 1), idea/script generation (Phase 4),
and video rendering (Phase 5) all run with zero network calls and zero API
keys. Phase 1/4 need only the Python standard library; Phase 5 additionally
needs Pillow (`pip install -r requirements.txt`) and a locally installed
free `ffmpeg` binary.

## Which future components may require paid APIs

None are *required*. `FutureAIVideoGenerator` (Phase 5) is the one
optional adapter for a paid service, and it is a placeholder interface
only - never called unless the site owner explicitly configures and
chooses it over the free `LocalVideoGenerator`.

## Persistent data

**Every piece of persistent data this agent ever writes lives in a local
JSON file** (or a plain `.jsonl` append log) under this directory -
`knowledge/features.json`, `data/logs/agent.log.jsonl`,
`data/analytics/*.json` (Phase 7), `ideas/*.json` (Phase 4), etc. No SQL,
no SQLite, no external database of any kind, matching the project's own
explicit requirement.

## Safety rules

Implemented (or, for phases not yet built, designed-in from the start so
later phases can't accidentally violate them):

1. **Never modify the GoOnlinePOS production application.** Every file this
   agent has ever written lives under `ai-marketing-agent/`. `scripts/
   analyze_product.py` opens GoOnlinePOS files with `Path.read_text()`
   only - it never calls `.write_text()` on anything under the repo root.
2. **Never delete GoOnlinePOS files.** No file in this directory issues a
   delete/write against anything outside `ai-marketing-agent/`.
3. **Never publish automatically in the prototype.** `agent/publishing/*`
   are unbuilt stubs; once built, dry-run is the only mode until real
   credentials *and* explicit approval are both present.
4. **Never invent product features.** Every entry in
   `knowledge/features.json` carries `evidence` anchors checked against the
   live GoOnlinePOS source on every run - see above.
5. **Never make unsupported marketing claims.** Planned idea/script
   generation will only read from `verified_only=True` features and will
   not use absolute/unverifiable superlatives.
6. **Never expose API keys or OAuth credentials in source code.** `.env`
   is git-ignored (`.gitignore`); only `.env.example` (placeholders) is
   committed.
7. **Use environment variables for secrets.** See `.env.example`.
8. **Log important agent decisions.** `agent/logger.py`'s `log_event()`
   is called by `analyze_product.py` on every run, appending to
   `data/logs/agent.log.jsonl`. Every future phase should call it too.
9. **Require explicit approval before future real publishing.** Designed
   into the publishing interfaces (dry-run default) even before they're
   implemented.
10. **Make every automated action reversible where possible.** Phase 1's
    only output is a regenerable JSON file (just re-run the script); no
    phase built so far performs any irreversible action.
11. **Store persistent data in local JSON files only; no database.** See
    "Persistent data" above.

## Roadmap - what's not built yet

Phases 1, 4, and 5 are complete and tested (see above). Everything past that
is still a **design**, not working code, per the project's own "work
incrementally... only then continue to the next phase" instruction:

- **Phase 6** - `YouTubePublisher`/`FacebookPublisher`, dry-run mode only
  (no real credentials configured, no real publish call - see "How
  publishing will eventually work" above)
- **Phase 7** - analytics JSON model + mock sample data
- **Phase 8** - the full agentic loop (`run-agent`), still
  create-then-review-then-dry-run only, no auto-publishing
- **Phase 9** - the remaining CLI commands, wired to the above once built

Each phase should be proposed, implemented, and tested on its own before
moving to the next, with a short report (what was created, what was
tested, what's next) - the same process Phases 1, 4, and 5 followed.
